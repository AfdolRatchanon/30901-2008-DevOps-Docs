หน่วยที่ (Unit)       7		ชื่อหน่วย (Name of Unit)     Testing & Quality Assurance
หัวเรื่อง (Sub Unit)/งาน (JOB) การทดสอบระบบ (Integration Test) และการตรวจสอบคุณภาพโค้ดบน Pipeline

1.  สาระสำคัญ (Concept) 
	นอกจากการทดสอบระดับฟังก์ชัน (Unit Testing) แล้ว ระบบจริงยังต้องทำงานร่วมกับฐานข้อมูลและบริการอื่น การทำ System Integration Test (SIT) จึงมีความจำเป็นเพื่อตรวจสอบการเชื่อมต่อทั้งหมดว่าทำงานประสานกันได้ดีหรือไม่ นอกจากนี้ในระบบอัตโนมัติ (CI/CD) จะต้องมีการตรวจสอบคุณภาพโค้ด (Quality Check) เช่น การใช้ Linter (ESLint) ค้นหาจุดผิดพลาดทางไวยากรณ์ การทำ Static Application Security Testing (SAST) เพื่อค้นหาช่องโหว่ความปลอดภัย ตลอดจนการทำ Performance Testing เพื่อดูขีดจำกัดการรับโหลดของระบบ สัปดาห์นี้จะมุ่งเน้นการนำเครื่องมือเหล่านี้มาประกอบรวมเข้าสู่ CI Pipeline อัตโนมัติ

2.  สมรรถนะหลัก/ย่อย (Unit of Competence / Element of Competence)
1. มีความเข้าใจหลักการทดสอบระบบแบบบูรณาการ (Integration Test)
2. สามารถใช้งานเครื่องมือตรวจสอบคุณภาพโค้ดและความปลอดภัยได้
3. มีทักษะในการนำชุดทดสอบทั้งหมดเข้าสู่ระบบ CI/CD Pipeline อัตโนมัติ
4. ปฏิบัติงานด้วยความตระหนักรู้ด้านคุณภาพและความปลอดภัยของระบบ

3.  จุดประสงค์เชิงพฤติกรรม (Behavioral Objective)
1. เขียน Integration Test ด้วยเครื่องมือ เช่น Supertest เพื่อทดสอบการรับส่งข้อมูลผ่าน API ได้
2. อธิบายความสำคัญและใช้งานเครื่องมือตรวจสอบคุณภาพ (Linter) หรือ SAST เบื้องต้นได้
3. ตั้งค่าการรันชุดทดสอบซอฟต์แวร์และการตรวจสอบคุณภาพแบบอัตโนมัติบน GitHub Actions ได้
4. กำหนดเงื่อนไข Quality Gate (เช่น Test Coverage ต้องถึงเกณฑ์) ก่อนอนุญาตให้ Deploy ได้
5. สรุปกระบวนการรวบรวมระบบทดสอบเข้าสู่ Pipeline ลงในสมุดจด
6. แสดงความเคารพและรับฟังความคิดเห็นจากเพื่อนในการแก้ปัญหาร่วมกัน
7. ประยุกต์ใช้การทำ Pipeline เพื่อกรองและสกัดกั้นซอร์สโค้ดที่ไม่ได้มาตรฐาน
8. ดำเนินการแก้ไขโค้ดอย่างอดทนเมื่อระบบ CI แจ้งเตือนข้อผิดพลาด (Failed)

5.  กิจกรรมการเรียนรู้ (Teaching / Learning Activities)

Integration Testing (SIT) 
คือการทดสอบโมดูลต่างๆ ทำงานร่วมกันได้อย่างไร ในกรณีของ Web API มักใช้เครื่องมือเช่น `supertest` ควบคู่กับเฟรมเวิร์กอย่าง Jest ในการจำลองการส่ง HTTP Request (เช่น GET /api/tasks) เสมือนว่าเป็นผู้ใช้จริงๆ และตรวจสอบสถานะ (Status Code) พร้อมข้อมูลที่ตอบกลับมา

Quality and Security Checks
- Linter (เช่น ESLint, Prettier): ใช้ตรวจสอบว่านักพัฒนาเขียนโค้ดตาม "มาตรฐาน" เดียวกันหรือไม่ (ตัวอย่างเช่น บังคับให้ใช้ Single Quotes หรือตรวจสอบการประกาศตัวแปรที่ไม่ได้ใช้)
- SAST (Static Application Security Testing): การสแกนโค้ดเพื่อหาช่องโหว่ความปลอดภัย โดยไม่ต้องรันโปรแกรม ตัวอย่างง่ายๆ เช่น การรัน `npm audit` เพื่อตรวจจับแพ็กเกจที่มีช่องโหว่

Quality Gate ใน CI/CD
ในการทำ CI Pipeline อัตโนมัติ เราจะนำสคริปต์เหล่านี้ (test, lint, audit) ไปใส่ใน GitHub Actions Workflow เป็น "ด่านตรวจคุณภาพ (Gate)" โดยตั้งเงื่อนไขว่า ถ้าด่านใดด่านหนึ่งล้มเหลว (Failed) หรือมีความครอบคลุมโค้ด (Coverage) ไม่ถึง 60% ระบบจะไม่อนุญาตให้รวมโค้ดและทำการ Deploy ขั้นตอนต่อไป

2. มีชุดคำสั่ง Integration Test สำหรับตรวจสอบการทำงานของ API

3. เพิ่มสคริปต์การทำ test และ lint เข้าไปในไฟล์ YAML สำเร็จ

4. GitHub Actions สามารถรันตรวจสอบสถานะโค้ดได้อัตโนมัติ

5. หากทดสอบไม่ผ่าน (Error/Coverage ไม่ถึง) Pipeline ต้องหยุดทำงานได้

2. คุณภาพของผลงาน

    2.1 วัดได้

           - Pipeline รันทุกขั้นตอนจนจบและแสดงสถานะเป็น Success (วงกลมสีเขียว)

           - ลำดับขั้นตอน (Step) ภายใน Job มีความต่อเนื่องสมเหตุสมผล

2. คุณภาพผลงาน

    2.1 วัดไม่ได้

         - ทักษะความพยายามในการอ่านและแก้ไขข้อผิดพลาดแจ้งเตือนจาก Linter 

         - ความรอบคอบและแนวคิดในการออกแบบ Quality Gate

3. เจตคติ (กิจนิสัยฯ) ในการทำงาน

   - ความตั้งใจและความมุ่งมั่นในการเรียนรู้การทดสอบระดับสูง

   - การไม่ลบ Test ทิ้งหนีปัญหา เพื่อให้ Pipeline เป็น Success อย่างไม่ถูกต้อง
