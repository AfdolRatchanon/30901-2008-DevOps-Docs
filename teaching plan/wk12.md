1.  สาระสำคัญ (Concept) 
	ในการทำงานจริง การทำ CI/CD จะต้องเกี่ยวข้องกับข้อมูลที่เป็นความลับ เช่น รหัสผ่านฐานข้อมูล คีย์การเชื่อมต่อระบบ (API Keys) หรือ Token สำหรับยืนยันตัวตน การนำข้อมูลเหล่านี้บันทึกลงในซอร์สโค้ดโดยตรงถือเป็นความเสี่ยงอย่างร้ายแรงทางไซเบอร์ นอกจากนี้ระบบองค์กรมักจะมีสภาพแวดล้อมที่ต่างกัน (เช่น Development, Staging, Production) สัปดาห์นี้จะมุ่งเน้นที่การใช้งาน GitHub Actions ขั้นสูง เช่น การปกปิดและจัดการตัวแปรความลับ (Secrets Management), การทำ Matrix Build เพื่อรันหลายเวอร์ชันพร้อมกัน และการควบคุม Pipeline แบบ Multi-environment

2.  สมรรถนะหลัก/ย่อย (Unit of Competence / Element of Competence)
1. เข้าใจหลักการรักษาความปลอดภัยของข้อมูลส่วนบุคคลและความลับในระบบ CI/CD
2. สามารถใช้ฟีเจอร์ขั้นสูงของ GitHub Actions เช่น Matrix และ Environments
3. มีทักษะในการจัดการ Multi-environment Deployment
4. ปฏิบัติงานด้วยความตระหนักรู้ด้านความปลอดภัย (Security Awareness) อย่างเคร่งครัด

3.  จุดประสงค์เชิงพฤติกรรม (Behavioral Objective)
1. อธิบายวิธีการจัดการตัวแปรความลับ (Secrets) ในระบบ GitHub ได้อย่างถูกต้อง
2. อธิบายและตั้งค่า Environments ในการสร้างเงื่อนไข Pipeline ได้
3. สร้าง Pipeline แบบแยกสภาพแวดล้อมการทำงาน (Multi-environment) ได้
4. ใช้งาน Matrix Strategy เพื่อรันการทดสอบ (Testing) ในหลายสภาวะแบบคู่ขนานได้
5. สรุปกระบวนการรักษาความปลอดภัยของรหัสผ่านใน CI/CD ลงในสมุดจด
6. แสดงความสนใจต่องานที่ได้รับมอบหมายได้เป็นอย่างดี
7. ประยุกต์ใช้ Environments เพื่อป้องกันไม่ให้โค้ดขึ้น Production โดยพลการ
8. ให้ความสำคัญและไม่นำข้อมูลความลับ (เช่นไฟล์ .env จริง) อัปโหลดขึ้น Repository โดยเด็ดขาด

Secrets Management
- ใน GitHub การเก็บข้อมูลรหัสผ่าน คีย์ API หรือรหัสเชื่อมต่อฐานข้อมูล จะต้องไม่เก็บในไฟล์โค้ด (เช่น ห้ามใส่ใน .env แล้ว Push)
- GitHub มีระบบ "Repository Secrets" ในหน้า Settings ให้เราป้อนคีย์เข้าไปเก็บแบบเข้ารหัส (Encrypted) 
- เวลาใช้งานในไฟล์ YAML จะดึงค่าผ่านตัวแปรพิเศษ `${{ secrets.ชื่อตัวแปร }}`

Multi-environment Pipeline
- โปรเจกต์ขนาดใหญ่จะมีสภาวะการรันซอฟต์แวร์ (Environment) แตกต่างกัน เพื่อใช้ทดสอบก่อนส่งมอบให้ลูกค้า
  1. Development (Dev): สำหรับโปรแกรมเมอร์ใช้ลองผิดลองถูก
  2. Staging / UAT: เหมือนระบบจริงทุกประการ เอาไว้ให้คนตรวจคุณภาพ (QA) ทดสอบ
  3. Production (Prod): เซิร์ฟเวอร์จริง ลูกค้าใช้งานจริง
- ใน GitHub Actions การแยก Environment ทำได้โดยกำหนด `environment: production` ภายใน Job ซึ่งเราสามารถเข้าไปตั้งเงื่อนไข (Protection Rules) ใน Repository ได้ว่า Environment นี้ ถ้าจะให้ Pipeline ผ่านเข้าไปทำงาน ต้องมี "คนกดยืนยัน (Approval)" เสียก่อน
